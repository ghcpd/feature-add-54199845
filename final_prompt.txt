## Problem Statement
## Header values ending with a newline no longer raise InvalidHeader

After upgrading to the latest version of requests, I'm seeing a strange behavior with header validation. Previously, if I accidentally included a trailing newline character in a header value (like `"bar\n"`), the library would immediately raise an `InvalidHeader` exception, preventing the bad header from ever being sent. Now it seems to silently accept it and tries to send the request anyway, which then blows up deeper in the stack with a `ValueError: Invalid header value` from what looks like Python's own HTTP internals.

The same thing happens if I set a header value to just `"\n"` — it used to be caught right away, but now it slips through.

I also noticed that header names with a trailing newline (like `"foo\n"`) are no longer caught either.

This is a security concern for me because my application constructs headers from user input (after sanitization), and I was relying on requests to be the last line of defense against header injection. The fact that bare newlines at the end of values are no longer rejected feels like a regression.

Here's a minimal example:

```python
import requests
from requests.exceptions import InvalidHeader

try:
    r = requests.Request('GET', 'http://example.com', headers={'foo': 'bar\n'}).prepare()
    print('BUG: no exception raised!')
except InvalidHeader:
    print('OK: correctly rejected')
```

On the previous version, this prints "OK: correctly rejected". On the current version, it prints "BUG: no exception raised!" (and if you actually send the request, you get a ValueError from somewhere deep in the HTTP stack).

My environment:
- Python 3.10
- requests latest from main branch
- Ubuntu 22.04

Maybe the validation regex was changed recently? I'm not sure what could cause newlines at the very end to be treated differently from newlines in the middle of a value (those are still correctly rejected).
